# PggTool / PggViewer — предложения по улучшению инструментов для агента

**Статус:** предложения (2026-09-08), ничего из этого не реализовано. Основание — не абстрактные пожелания, а конкретные места, где за последние сессии агент упирался в инструмент и делал работу в обход (numpy, `cmp` по OBJ, `xvfb-run` с ручным подбором орбиты). Каждый пункт привязан к такому инциденту.

Главный пользователь PGG — кодинг-агент. Для него инструмент — это единственный способ **увидеть** результат: он не крутит модель мышкой, не ставит брейкпоинт в Blender, а задаёт вопрос к CLI и читает текст. Значит критерий качества инструмента — «сколько вопросов агент может задать, не выходя из CLI, и насколько ответ детерминирован и diffable». Сейчас PggTool хорошо отвечает про *геометрию мешей* (`--probe … :schema/stats/coverage/table`) и не отвечает почти ни на что про *поля и SDF*, про *качество меша* и про *изменения между прогонами*.

Текущий контракт пробников (§9 спеки, реализация E6): `path:inspector[param=value,...]`, инспекторы `schema · stats · coverage · table`, флаги `run --probe/--debug/--obj/--param/--output/--lib`. Все предложения ниже расширяют этот контракт, а не вводят параллельный.

## 1. Сэмплирование полей и SDF (приоритет 1)

**Инцидент.** Расследование `mc_thin_shell_slivers.md`: чтобы понять, что «оболочка 0.12» на торце на самом деле стенка 1 см, а грань лежит ровно на узле решётки, потребовалось *посмотреть значения поля в точках*. PggTool этого не умеет — пришлось переписать SDF-композицию (`gable_prism`, `slab_at`, instance с `@orient`) на numpy и сверять с OBJ. Это час работы и риск расхождения с движком; автор брифа этого не сделал и ушёл по ложной гипотезе. Правильный ответ занял бы одну команду.

### 1.1. `sample` — значение в точках

```
--probe 'shell:sample[at=0,1,3.425]'
--probe 'shell:sample[at=0,1,3.425;0,1,3.40;0,1,3.45]'      # несколько точек через ;
--probe 'shell:sample[from=-2.73,0.3,-3.4,to=-2.53,0.3,-3.4,n=41]'   # профиль вдоль отрезка
```

Для `sdf` — значение поля; для `geo` — ближайшая точка/грань и расстояние (для мешей — знак через `sdf_from_mesh`-псевдознак, честно помеченный). Вывод: `x y z value` построчно, `%g`, детерминированно. Профиль — то, что нужно для «где ноль, где излом, какой градиент».

### 1.2. `slice` — срез поля картой

```
--probe 'shell:slice[axis=z,at=3.425,step=0.25]'                   # ASCII: # внутри, . снаружи
--probe 'shell:slice[axis=z,at=3.425,step=0.05,format=csv]'        # значения таблицей
--probe 'shell:slice[axis=z,at=3.425,step=0.05,format=png,out=/tmp/s.png]'
```

Границы — conservative bbox поля (или `bounds=…`). ASCII-карта на 30×20 символов — это ровно то, что в расследовании мгновенно показало «отрицательная область = треугольник щипца, стенка 1 см». Для агента ASCII важнее PNG: он читает текст в контексте, картинку — через отдельный тул.

### 1.3. `lattice` — решётка `mesh_from_sdf` глазами автора

```
--probe 'shell:lattice[voxel=0.05]'
```

Печатает начало/шаг/размеры решётки, которые получит `mesh_from_sdf` с этим `voxel`, и — главное — **предупреждения**: осевые грани примитивов DAG, лежащие ближе 0.05·voxel к плоскости решётки; пары параллельных граней на расстоянии < 2·voxel (фича тоньше двух вокселей — кандидат на пропадание/рвань). Второе выявило бы 1-см торцы `gable_prism` до того, как они стали багом.

### 1.4. `--eval` — поле по месту

```
PggTool run cottage.pgg --eval 'fbm(scale = 2.2, octaves = 3, rng = split_rng(root_rng, key = "stone"))' --on masonry --probe ':stats'
```

Вычислить произвольное выражение-поле в контексте файла (доступны его binding'и) на заданной геометрии и прогнать через стандартные инспекторы. Закрывает вопросы вида «какой разброс у этого шума на самом деле» без правки файла и без `set(...)`-заглушек. Реализация — синтетический binding поверх `FlatProgram`, семантика та же, что у `set(on, "tmp", expr)`.

## 2. Диагностика качества меша (приоритет 1)

**Инцидент.** В оболочке крыши 12 % треугольников были нулевой площади — никто не знал, пока я не посчитал их numpy-скриптом. `nonManifoldEdgeCount` есть в тестах, но не в CLI. При первом варианте фикса появились 6 non-manifold рёбер — узнал из голден-теста `tower` через две минуты прогона, а не из `--probe`.

### 2.1. `check` — инспектор здоровья меша

```
--probe 'house:check'
```

Одна запись: degenerate faces (нулевая площадь / повторяющиеся индексы), non-manifold edges, boundary edges (открытые), isolated points, NaN/inf в `@P`/`@N`/`@Cd`, faces с несогласованной ориентацией по компонентам, число компонент связности, min/median длина ребра, доля «иголок» (aspect > 20). Всё это дёшево и детерминированно. Пороговые параметры — `[warn_aspect=20]`.

### 2.2. `table[where=…]` и `find`

```
--probe 'house:table[where=abs(@N.y) < 0.05 & @P.y > 3.3, limit=50]'
--probe 'house:find[where=ingroup("edge") & @Cd.r > 0.9]'      # только счётчик + bbox подмножества
```

Сейчас `table` — первые N элементов; для расследований нужны *отфильтрованные*. Предикат — обычное поле PGG (уже есть парсер и eval), домен — как у binding'а. `find` без строк — быстрый ответ «сколько и где» (count, bbox, список групп).

### 2.3. `--obj` по группам и с диагностическими цветами

```
--obj /tmp/out --obj-split-groups          # house.roof.obj, house.tile.obj, ...
--obj /tmp/out --obj-color=check           # @Cd подменяется: degenerate/non-manifold/boundary — цветом
```

Сегодня бахрому локализовали, подсвечивая группы в PggViewer вручную. Экспорт по группам делает то же самое одним flag'ом и дальше работает любой внешний просмотрщик.

## 3. Сравнение прогонов и регрессия (приоритет 2)

**Инцидент.** Каждая декомпозиция `cottage.pgg` (вынос `lantern`, `window`, модули `cottage/*`) проверялась `cmp` двух OBJ — «бит в бит». Это работало, но через файлы и внешнюю утилиту; при отличии `cmp` говорит только «байт N».

### 3.1. `run --fingerprint` и `diff`

```
PggTool run cottage.pgg --fingerprint                  # per-output: hash позиций/топологии/атрибутов, отдельно
PggTool diff a.pgg b.pgg [--output house]              # что изменилось: counts, bbox, max |ΔP| по сопоставленным точкам, какие атрибуты/группы появились/исчезли
PggTool diff --baseline /tmp/house.fp cottage.pgg      # против сохранённого fingerprint
```

Fingerprint уже есть в ядре (кэш §5.3) — его надо только вывести. `diff` для мешей с равным числом точек — поточечный; для разных — по bbox/counts/группам. Это превращает «переставил def'ы, ничего не сломал?» в одну команду с ответом `identical` / `ΔP max 0.0008 (vines)` — второе как раз был реальный случай, найденный вручную.

### 3.2. Голдены как файлы, а не литералы в тестах

Сегодня golden-счётчики `sphere/rock/wall/fracture/tower` — литералы в `*_test.cpp`; фикс фазы решётки означал ручное переснятие 40 чисел скриптом по gtest-выводу. Предложение: `src/tests/pgg/goldens/<name>.fp` (текст, diffable), тест сравнивает fingerprint, `PggTool run --update-goldens` переснимает. Снижает цену любого честного изменения численного профиля.

## 4. PggViewer как headless-рендер (приоритет 2)

**Инцидент.** Каждый скриншот — `xvfb-run -a … PggViewer file --preview=house --preview-orbit=255,5,0.9 --shot=… --shot-delay=14`, подбор орбиты на глаз, невозможно «посмотреть на дверь»: орбита крутится вокруг центра bbox всего дома. Обход — `--preview=door` (рендер промежуточного binding'а), который не показывает контекст.

- `--preview-target=x,y,z` или `--preview-target=group:lamp` / `--preview-target=binding:door` — центр орбиты и fit по bbox цели, остальная сцена остаётся.
- `--preview-fit=all|target` и `--preview-distance=`.
- `--shot` без задержки: рендер по готовности (`--shot-delay` остаётся как override) — сейчас 14 с ждём вслепую.
- `PggTool render <file> [те же флаги]` — тонкий вызов того же кода без окна (offscreen GL или software rasterizer на 800×600 — для агента достаточно). Убирает `xvfb-run` из типового цикла и делает рендер доступным на CI.
- `--preview-highlight` уже есть; добавить `--preview-wire` и `--preview-ortho=front|side|top` — ортопроекции сильно упрощают чтение размеров агентом.

## 5. Ошибки и справка для агента (приоритет 2)

**Инцидент.** Ложный E302 при `value(@wid, on = a)` внутри def-аргумента искался полдня: сообщение говорило «атрибута нет на этой геометрии», не говоря *на какой* и *откуда пришло поле*. Отдельная тема — «спека в контексте»: агент вынужден держать в голове весь §8, `docs <file> <symbol>` работает только для def'ов файла.

- `check --explain E302` — карточка кода: что значит, типичные причины, пример с фиксом. Источник — таблица кодов §12 спеки, генерируется, не дублируется руками.
- В сообщениях E302/E204/E606 — **путь binding'а, на котором проверяется**, и цепочка инлайнинга (`field consumed by set_position on bx[0].out ← arg w of bx ← value(@wid, on = p1)`).
- `docs builtin <name>` (`docs builtin clip`) — сигнатура + абзац из §8 спеки + один пример; `docs builtins [--group topology|sdf|fields]` — список сигнатур одной строкой каждая. Это то, что агент реально хочет вместо чтения 1000-строчной спеки: короткий, точный ответ на «как называется параметр и какой у него дефолт».
- `run --json` — как у `check`: выходы, пробники, диагностики машинно; сейчас парсим текст.
- `check` должен предупреждать про паттерн `inner.w = outer.w − 0.02` из п. 1.3 через `lattice`-эвристику, когда в графе есть `mesh_from_sdf` — W-код с текстом «стенка тоньше 2·voxel».

## 6. Профилирование (приоритет 3)

`house` считается 16 с в превью; агент не знает, где. `run --profile` — таблица по binding'ам: время, число field-eval'ов, cache hit/miss, объём геометрии на выходе; сортировка по времени, top-20. Данные в движке частично есть (`bindingFieldEvals`, счётчики кэша) — не хватает вывода. Для `bake_ao`/`mesh_from_sdf`/`realize` — отдельные строки внутри.

## 7. Что НЕ предлагается

- REPL/интерактив — агент работает вызовами, ему нужны идемпотентные команды с полным выводом, не сессия.
- Графический дебаггер узлов в PggViewer — вью для человека; агент туда не смотрит.
- Свой формат вместо OBJ — OBJ читают все; нужны расширения экспорта (группы, цвета), не замена.

1. §1.1 `sample` + §1.2 `slice` (ASCII) + §2.1 `check` — три инспектора на существующем контракте пробников, каждый ≤ 200 строк в `engine.cpp`/`probe.cpp`; закрывают оба реальных расследования последних дней.
2. §3.1 `--fingerprint`/`diff`; §4 `--preview-target` и `--shot` по готовности.
3. §2.2 `table[where]`, §1.3 `lattice`, §5 `docs builtin`/`--explain`, `run --json`.
4. §3.2 голдены-файлы, §4 `PggTool render`, §6 `--profile`, §1.4 `--eval`.

Критерий приёмки для каждого пункта одинаковый: команда, которую агент вызвал бы в соответствующем инциденте, и её ожидаемый вывод — фиксируются тестом в `src/tests/pgg/probe_test.cpp`; в `implementation.md` дописывается абзац про инструмент; в спеку (§9) — только контракт инспектора.
