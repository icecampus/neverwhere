# Из shadertoy-демки в геометрию движка (playbook)

Рецепт переноса процедурной SDF-демки из `docs/reference/shadertoy` в меш-генератор
движка. Отработан на «Voronoi - rocks» → `stone_gen` + StoneCubePlayground
(коммиты `73ce80b`, `50e54f3`, `e8ad617`). Цель документа — чтобы следующая
демка портилась по чек-листу, без повторного наступания на грабли.

## Дорога

```
shadertoy-референс
  → ShadertoyPlayground        (оригинал крутится как есть, смотрим look)
  → <name>_gen (no-GPU либа)   (C++-двойник SDF — КАНОНИЧЕН; тесты, меш, экспорт)
  → <Name>Playground           (Raymarch = look-reference, Mesh+Procedural = цель)
  → render_core                (перенос процедурного шейдера, образец — CliffRenderer)
```

Ключевая мысль: **SDF/генератор живёт в C++ без GPU** (тестируемо, мешится,
бейкается, экспортируется), а **материал — попиксельный процедурный шейдер из
world-позиции**, а не запечённая текстура.

## Принципы

### 1. C++-двойник SDF каноничен, GLSL — look-reference
Первым делом портируется `map()` демки в чистую C++ либу (`stone_gen` —
образец: `StoneCubeParams` → `StoneSdf` с `eval/map/normal/bumpNormal/
ambientOcclusion/albedo`). Никаких Qt/GPU-зависимостей. GLSL-шейдер
плейграунда остаётся эталоном картинки; при расхождениях прав C++.

### 2. Хэш — только pcg3d, бит-в-бит в GLSL и C++
`fract(sin(x)*43758)` на больших аргументах даёт направленные полосы.
Целочисленный `pcg3d` дублируется одинаково в обоих языках (см.
`stone_sdf.cpp` ↔ `StoneCubeSdfGlsl.cpp`) — поля/сетки/сборки совпадают.

### 3. Меш — через `cliff::ScalarFieldView` (общая точка входа surface nets)
Образец — `stone_mesh.cpp`:
- домен = bbox объекта + максимальный выступ (bulge+bevel+fbmAmp) + padding;
- сэмплирование поля в grid (`nx` = воксели, точек `nx+1`);
- `blurPasses` (3-tap) — naive surface nets террасит на крутых бороздах SDF;
- `regularizeSigns` → `extractSurfaceNets` → `checkWatertight`;
- **acceptance gate: `remainingSaddles == 0` и `watertightBadEdges == 0`**
  (проверяется в gtest и в smoke).

### 4. Материал — процедурный, НЕ текстура
Прецедент — `cliff_renderer.cpp`: в вершине только грубые данные (у клифов —
один float `groove`), всё остальное считается во фрагментном шейдере из
интерполированной world-позиции. Для stone cube: voro-тинт, мох, борозды,
fbm-бамп, AO, soft shadow — тот же блок, что в реймарч-шейдере, только
позиция приходит из растеризатора.

Почему не бейк (болезненно проверено на UV-атласе):
- швы/углы атласа структурны и не лечатся до конца;
- фиксированное разрешение + мип-блюр против детали вблизи;
- бейк десятки секунд → параметры перестают быть живыми слайдерами;
- уникальные текстуры на каждый вариант ассета против одной формулы.

Бейк (OBJ+PNG) оставить как **экспортную/отладочную утилиту**, не основной путь.

### 5. Per-vertex — грубое, per-pixel — тонкое
Каналы в вершинах интерполируются линейно: годится для широких масок
(глубина борозды клифа, AO), не годится для тонкой детали (борозды камней,
бамп) — её пересчитываем из world-позиции попиксельно, это дёшево.

### 6. AO/тени — единственное, что стоит SDF-тапов
В плейграунде: per-pixel `calcAO` (5 тапов) + `softShadow` (32 тапа) прямо в
шейдере — точно и просто, т.к. SDF там уже есть. Прод-вариант для слабого
железа: один per-vertex float AO, запечённый при генерации меша (меш плотный,
этого хватает), плюс затемнение по cellFactor.

### 7. Перф: тяжёлый попиксельный шейдер → scaled offscreen target
На 2x-DPI фреймбуфере (2560×1440) процедурный шейдер полз (230 мс/кадр);
рендер в пониженный target + blit (как у реймарча и ShadertoyPlayground) →
13 мс при scale 0.5. Время кадра линейно по пикселям (GPU-bound).

### 8. Smoke — обязательный acceptance-ритуал
`--smoke` гоняет сборку меша/бейк/рендер программно, логирует
`TEST PASS`/`TEST FAIL` и **возвращает ненулевой exit code при провале**
(регрессия, найденная ревью: TEST FAIL с exit 0 — ложная зелень).

## Чек-лист портирования следующей демки

1. **Референс.** Код в `docs/reference/shadertoy/<name>/` + README (источник,
   лицензия, текстуры iChannel). Прогнать в ShadertoyPlayground
   (`--demo`, `--cube`) — убедиться, что look понятен.
2. **Декомпозиция.** Выделить `map()` (форма, SDF) отдельно от материала
   (тинт/мох/бамп). Список параметров → 4×vec4 uniform-блок (shape/look).
3. **Либа `<name>_gen`** по образцу `stone_gen`: params struct, SDF-класс,
   pure pipeline. gtest: знаки SDF (внутри/снаружи), детерминизм, вариация
   сидом.
4. **Меш** по образцу `stone_mesh.cpp` через `ScalarFieldView`. gtest:
   watertight=0, saddles=0, вершины в домене.
5. **Плейграунд** по образцу StoneCubePlayground: Raymarch (look-reference) +
   Mesh+Procedural (цель) режимы, debounce-ребилд 0.3 с только по
   shape-параметрам, CLI `--smoke`/`--shot`/`--proc`.
6. **Процедурный шейдер** = материал-блок реймарч-шейдера, позиция из
   растеризатора. Приём проверки: скриншоты Raymarch vs Procedural
   совпадают картинкой.
7. **Перенос в render_core** (когда look устаканился): по образцу
   CliffRenderer — per-vertex attrs + процедурный FS, параметры ассета в
   uniforms.

## Грабли (все из практики этого проекта)

- **Raymarch banding** («шторка» полос): это квантование глубины хита.
  Лечится секант-уточнением хита + широким стенсилом нормали (0.004),
  а НЕ более мелким eps.
- **fbm-градиент для bump** — десятки единиц: без кепа `g/(1+|g|)` нормаль
  рандомизируется в радужный шум. В бейке стенсил ~1–2 текселя (low-pass).
- **GLSL 330:** `const float x = <uniform-выражение>` не компилируется;
  Apple-компилятор резервирует `noise1..4` (переименовывать).
- **sokol VB stride:** если пайплайн использует часть атрибутов буфера,
  `layout.buffers[0].stride` выставлять ЯВНО (иначе sokol выводит stride из
  перечисленных атрибутов и fetch ломается).
- **std140:** порядок `glsl_uniforms` = порядок объявлений в шейдере;
  `static_assert(sizeof(Uniforms) == N*16)`.
- **ImGui:** `"...\0..."` в строках с цифрами — восьмеричные escapes
  (`"256\0512"` это `')'`, не NUL). Массив `const char*[]` вместо
  `\0`-разделителей.
- **stb:** `STB_*_IMPLEMENTATION` — в одном TU на бинарь (у нас —
  `stone_bake.cpp`).

## Масштабирование: кубик → хайграунд (открытые вопросы)

Кубик — это «одна ячейка материала» в вакууме. Для каменной стены как
поднятой земли предстоит решить:

- **Домен:** не bbox куба, а полоса вдоль границы raised-ландшафта (как
  сейчас cliff-field в `highground_core`); вероятно, каменный стиль станет
  ещё одним `IWallStyle`/`CliffRenderer`-вариантом, а не отдельным слоем.
- **Чанкинг и сиды:** стена большая — генерация по чанкам карты со стабильным
  сидом (voro/seed уже параметризованы, соседние чанки должны сшиваться по
  общим ячейкам вороного — масштаб ячеек привязывать к мировым координатам,
  не к чанку).
- **Плотность меша vs бамп:** силуэт стены задаёт меш (cellSize), мелочь —
  попиксельный бамп; баланс подобрать на реальной карте (в плейграунде
  0.04 ≈ 62k tris на куб 2³ — для карты это много, укрупнять и компенсировать
  бампом).
- **Свет:** в редакторе изометрический постоянный `view_dir` (как у клифов) —
  soft shadow per-pixel можно заменить дешёвым AO/groove-затемнением.

Когда будем браться — сначала смотреть `cliff_renderer.cpp` (инфраструктура
per-vertex + процедурного FS уже есть) и `src/libs/landscape_mesh`
(`IWallStyle` — точка подключения стилей стен).
